# 对话执行与上下文管理评估

日期：2026-09-03。检查基线：`f395bbf67cec7f65426b814f3014ac7d564b3ae7`。

本文是评估与设计建议，未修改运行时、现有 run 或用户确认记录。没有拿到用户提到的那次任务对话，因此可以证明机制缺口，不能判定那次跳步究竟来自入口未加载、误记确认，还是上下文恢复错误。

## 结论

当前 harness 对产物的分层、引用关系、版本和渲染结果约束较强，对“理解是否充分、问题是否处理、方案是否展示、用户是否接受”的约束明显较弱。上一轮修复增强了文件与交付完整性，没有建立完整的对话状态机。

不宜用“agent 是否认真”解释全部问题，也不能把“不提问”当作“没有不确定性”。建议把专业协作者应做的事情落实为可检查的工作成果：复述目标、声明推断、列出关键未知、展示逻辑链、记录具体版本的用户决策、说明下一步。模型内部是否真正理解不可由这些字段直接证明；这些成果可以帮助用户发现理解偏差。

应区分三个维度：

- **内容充分性**：论断及其证据、适用边界、反例能否支撑目标。
- **用户决策**：哪些偏好已明确、哪些由用户委托、哪些仍待选择。
- **执行完整性**：必要步骤是否完成、对应哪个版本、恢复后从哪里继续。

## 本地证据与风险

最小探针使用现有测试中的合成材料，在独立临时 run 中执行真实 CLI；未修改任何真实 run。结果见 [探针记录](2026-09-03-dialogue-context-probe.json)。

| 优先级 | 发现与证据 | 影响 |
|---|---|---|
| P1 | `comh/cli.py:149` 的 confirm 校验新鲜度与内容；`comh/manifest.py:229` 只保存 `confirmed/at/hash`。探针在没有真实用户输入的情况下确认了两个 gate | CLI 能证明确认记录与文件对应，不能证明展示与同意发生过。相同 agent 可连续调用 save/confirm/render |
| P1 | `stages/brief.md:10` 鼓励推断，但没有提问决策规则；schema 中 voice、场合、视觉方向不是必填，open_questions 只要求 question、不要求答案或处理方式 | 探针中三项缺失且留有未回答的受众问题，Gate 1 仍有效。“字段存在”也不能区分用户原话与模型推断 |
| P1 | `GATE_OF_ARTIFACT` 只有 brief/narrative；`stages/report.md` 从计划直接进入正文，deck 阶段也无大纲确认状态 | 探针在没有大纲确认的情况下成功保存并渲染 deck。故事线后先粗后细的协作不是现有契约 |
| P1 | `validate_claims` 检查状态、引用和估读，但不检查关键未知的处置记录 | 探针中 primary claim 标为 needs_research、没有处置决策，也可确认 narrative。保留未知本身可以合理，但应展示并决定如何影响结论 |
| P1 | 仓库只有 `skill/SKILL.md`，没有 `.agents/skills` 发现入口；安装说明只安装 Python 包，package-data 未包含 stages/references | 不能假定安装 CLI 就自动加载操作协议。需分别验收源码使用与安装分发；这不证明用户那次会话一定未加载 |
| P2 | `comh status` 只显示 artifact/gate/delivery；没有正在展示的方案、待回答问题、用户拒绝的方向、当前打磨粒度 | 压缩或换会话后，saved 容易被当作已对齐，旧推断容易被当作已确认 |
| P2 | skill 路由直接进入 evidence；evidence 要求全部材料、每图、逐页阅读，brief 在其后 | 未定问题便全面提取，可能消耗大量无关上下文；当前缺少轻量 intake 与按问题补证据的路线 |
| P2 | `evidence/coverage.yaml` 只出现在阶段提示词，运行时代码不读取。探针未生成该文件仍能推进 | 缺少覆盖日志不会被发现；有日志也不能证明实际阅读。应分别检查记录完整性与提取质量 |
| P2 | evidence-pack 输出节点与引用链，不含 brief 约束、当前 gate 状态、相关决策、反证和任务位置 | 局部修复节省上下文的同时，可能遗漏全局意图或未被作者引用的反证 |
| P2 | schema 的 hard constraint 描述仍写不可检查时 demote；deck 阶段要求 style findings 清零，而 QA 允许有理由地保留 warn | 同一契约有冲突版本，增加误执行；应清除重复定义，由一处规则拥有含义 |

现有测试很好地验证了文件完整性，不能据此宣称 agent 的真实对话遵循率合格。探针中的主动 confirm 仅用于展示 CLI 的能力边界，并非真实工作中可绕过用户同意的授权。

## 沟通契约：覆盖所有关键决策，不必逐项审问

推荐的提问条件是：**信息缺失或冲突，而且答案会改变当前方案；同时无法从已授权材料或已有用户指示中可靠取得。** 不用模型自报的“信心 95%”作为跳过提问的依据。

| 信息类别 | 处理方式 | 举例 |
|---|---|---|
| 用户已明确说明 | 提取原话或消息引用，简短复述，不重复问 | 已说“中文、给客户、20 分钟” |
| 影响目标或结构的未知 | 当前阶段提出具体问题，并说明不同答案如何改变方案 | 争取预算还是技术评审；是否允许提出因果结论 |
| 能通过材料查清的事实 | agent 自己检索、计算或核验；不把调查工作推给用户 | 单位、样本量、两份表格的口径 |
| 可逆、低影响的偏好 | 给出推荐默认值并标明来源，允许修改 | 没有品牌限制时的初始排版方向 |
| 下游才有影响的选择 | 记录延期，在首次影响工作前提出 | 动画细节、插图裁切、逐页措辞 |
| 不适用于所选媒介 | 记录不适用及理由 | 纯文字报告不必讨论幻灯片动画 |

每个契约维度都应有处置，不要求每个维度都产生一轮对话。建议在既有 brief 增加结构化对齐记录：字段、值、来源（用户/材料/推断/默认）、状态（待确认/已确认/委托/延期/不适用）、依据、影响、最晚决定阶段。关键待确认项阻止对应阶段获准推进；延期项在截止阶段重新成为待处理项。

value 与对齐记录应交叉检查，避免出现两套不一致的契约；核心值继续由 brief 拥有。用户原话是依据，模型推断不能自动升级为“用户确认”。没有未知时，给出简短的目标复述与所用依据即可，不强迫发明问题。

建议在 Gate 1 展示一张简短的理解摘要：

> 我的理解：这次给客户技术负责人说明试验结果，目标是决定是否开展试点。\
> 已明确：中文，20 分钟，需要交付报告和演示稿。\
> 我的建议：先展示结果，再解释机制；这是提案，尚未视为你的决定。\
> 需要你决定：试点建议是否包含成本承诺？这会改变结尾及所需证据。\
> 当前证据边界：只有受控负载结果，无法直接代表线上收益。

这是可审查的工作摘要，不是要求输出模型内部推理过程。

## 故事线与大纲：分别对齐，精修深度由用户选择

建议的常规路径：

```text
轻量 intake：目标草案、材料清单、协作方式
    ↓
按目标提取证据 ↔ 暴露缺口、补材料、修正目标
    ↓
沟通契约摘要 → 用户确认 Gate 1
    ↓
论断与证据状态 → 媒介无关故事线 → 用户确认 Gate 2
    ↓
按媒介给粗大纲 → 用户确认结构或明确委托细化
    ↓
可选打磨：结构 → 各部分要点和证据 → 页/节细节
    ↓
正文与视觉样张 → 渲染 → QA → 用户验收
```

intake 是研究范围的草案，不预先决定事实和结论。默认仍在有限的初步证据检查后确认 Gate 1；之后发现证据改变目标时重新对齐，不能为避免返工而隐藏新情况。

故事线应先回答“观众目前怎么想、要接受哪些判断、为什么能走到下一步、最后接受什么”，展示主论断、证据状态与边界。不要只列主题词，也不要提前塞入页数、颜色和布局。

例如，同一故事可以是“现有延迟妨碍目标 → 受控试验显示改善 → 改善存在条件 → 因此建议有限试点”。演示稿大纲随后决定开场、结果页、边界页、行动页；报告大纲可以把方法与完整数据提前。两种媒介共享论断，分别决定展开方式。

建议提供三个协作档位，进入任务时依据用户已有要求选定或只问一次；随时允许切换：

| 档位 | 用户参与程度 |
|---|---|
| 关键节点对齐（建议默认） | 契约、故事线、粗大纲各展示一次，认可后自主细化 |
| 一起打磨 | 在上述基础上，逐部分从结构到要点、再到细节；每次只处理一个明确问题 |
| 委托出稿 | 用户明确委托的细化步骤可连续完成；保留委托范围、当前假设和证据边界 |

“不用逐页磨”只减少细化轮次，不能被推断为“故事线已经确认”。用户确实委托某个决定时，将状态记为 delegated，不能写成用户已审阅具体内容；既有故事线确认默认保留。扩大委托范围必须来自新的用户指示。

大纲优先由 deck_plan/report_plan 的结构字段生成审阅视图，不维护重复的 outline.md 真相源。确认记录绑定页/节顺序、要点职责、beat 覆盖和取舍的结构指纹；后续补样式不应无故重问结构。结构字段变化需要重新对齐，或引用已授权的具体修改；代码不猜测任意文本改动是否“语义等价”。若草稿无法满足正式 plan schema，允许专用草稿状态，并阻止其被当作完整成品渲染。

## 从 gate 标记到可恢复的用户决策

推荐的协议状态为 `draft → presented → awaiting_user → accepted / changes_requested`，另有明确的 `delegated`。任意 accepted 必须针对当前方案版本；presented 不能自动转换为 accepted。

待确认请求至少绑定：run、阶段、具体 artifact/结构哈希、摘要及其哈希、请求 ID、提出时刻。决策至少记录：请求 ID、接受/修改/委托、用户原话或可信消息引用、适用范围和时刻。方案变更、回复对应错误请求或缺少前置确认时，不能推进。

分两种落地强度，必须诚实区分：

1. **便携 CLI 协议**：agent 代录真实用户回复，CLI 检查请求、版本和顺序。能减少遗漏并提供审计，不能认证回复来自真人；agent 仍可能错误代录。
2. **宿主集成**：由独立于内容生成 agent 的宿主接收用户回复，并向受控 gate 服务提交授权事件；该服务的数据和凭据不向生成 agent 开放。等待由 runtime 执行。这样才可以在该受控执行面阻止 agent 自己确认。

在拥有任意 shell 和同等文件写权限的通用 agent 环境中，加 nonce、签名字段或“已问用户”布尔值都不能凭空形成授权边界。只增加更多确认口号会继续留下同样的问题。也不建议为此立即引入大型编排框架；先把便携协议与宿主接口区分清楚。

暂停期间可以继续已授权、互不依赖的调查，不能越过正在等待的内容决策。恢复请求需要幂等，避免重复登记同意、重复渲染或把旧回复应用到新方案。

## 渐进式披露与上下文恢复

已有合理基础：入口 skill 28 行、1,374 个字符；stages 与 references 分文件；evidence-pack 沿 ID 链取切片。实测所有阶段和参考文档合计 23,096 个字符，其中 deck 阶段 6,936 个字符。这里统计字符，不假装是 tokenizer 的 token 数，也不能仅凭长度断言模型会失败。

缺口在于分文件后仍靠 agent 自己猜“何时加载什么”，缺少任务状态、检索预算与恢复契约。建议明确四层：

| 层 | 默认加载内容 | 按需追加 |
|---|---|---|
| 入口 | 任务用途、最小不变量、如何获得当前状态 | 不展开所有阶段 |
| 当前阶段 | 目标、已确认约束、当前状态、待决问题、允许动作、完成条件 | 本阶段 schema 与少量例子 |
| 当前工作单元 | 相关 beat/claims/evidence，来源 locator、相关反证、前后衔接 | 原文片段、必要图片 |
| 专项资源 | 只给路径和触发条件 | 到渲染时再读模板、动画、主题、编译细节 |

建议提供 `comh next --json` 与 `comh context --stage ... [--node ...]`（拟议接口，当前不存在）：由同一状态机计算下一步与上下文包，不能另造一个会漂移的 prompt 路由器。上下文包包含指令版本、artifact 哈希、生成时刻、未加载内容清单、继续检索方式和明确的 stop 条件；每次读取重算状态。

大材料先建目录与来源覆盖索引，再围绕论断逐步提取。声明全量阅读时仍须完成并记录对应覆盖；普通任务允许有理由的相关性筛选。局部包始终保留全局目标、硬约束、核心不确定性和叙事骨架，不能只取支持证据而过滤反证。到 Gate 2 与最终 QA 仍进行全局一致性审查。

接力状态推荐放在受版本管理的 `run.yaml`（交互部分）及按需查阅的决策日志中；已有 brief/narrative/plan 继续拥有内容。恢复摘要从这些结构化状态生成，不让手写摘要成为第二套真相源。必须保留：用户最新指示及来源、委托范围、待确认请求、已拒绝方向、当前细化粒度、阻塞项、下一动作和相关文件指针。摘要不得把推断写成决定，也不得仅凭 saved 自动继续。

本 harness 可以控制自己输出的上下文包，无法从普通 CLI 删除宿主已经加载的消息或保证宿主如何压缩。需要分别记录“包里提供了什么”和“在特定 runtime 中实际看到了什么”。多 agent 不是必需条件；已有独立读者测试确有价值时，应使用独立上下文并保留输出，缺能力时报告缺失，不能勾选已完成。

## 可借鉴的公开实践

以下是经读取的一手材料；借鉴的是机制，未安装或执行这些项目的技能。

- **OpenAI Skills**：元数据先用于发现，选中后加载正文，再按需读取辅助资源。这支持轻入口设计，也说明必须验收 skill 的实际发现路径。[官方说明](https://learn.chatgpt.com/docs/build-skills)
- **Superpowers**：提问聚焦、方案按块展示、复杂工作分层对齐，可用于“共同打磨”模式。其每个任务都重新批准的强规则会增加日常修改摩擦，不宜整体移植；它本身也主要依赖 agent 遵守提示词。[固定版本](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/skills/brainstorming/SKILL.md)
- **OpenSpec**：由 artifact 依赖关系提供状态与当前指令，区分项目上下文、当前 artifact 规则和模板。适合参考 context/next 接口；其偏流动、弱阶段锁定的取向不能代替本项目的用户确认要求。[固定版本实现](https://github.com/Fission-AI/OpenSpec/blob/e062b9572be933564ba3899d059377dfa1393e32/src/core/artifact-graph/instruction-loader.ts)；[定制规则](https://github.com/Fission-AI/OpenSpec/blob/e062b9572be933564ba3899d059377dfa1393e32/docs/customization.md)
- **LangGraph**：持久化暂停点，外部输入恢复；恢复可能重跑节点，副作用须考虑幂等。适合作为宿主集成参考，框架本身不自动证明调用 resume 的人是用户。[官方 interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)
- **Anthropic context engineering**：保留轻量路径和标识，按需检索，结合压缩与外部笔记。可用于材料索引和接力摘要；这是工程建议，不是本仓库改造有效的实测证明。[一手文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

## 建议实施顺序与验收

| 批次 | 范围 | 完成条件 |
|---|---|---|
| 1：对话契约 | intake、提问决策规则、brief 对齐记录、未知处置、协作模式；清理相互矛盾的提示 | 缺少关键决定不会获准推进；已给答案不重复询问；默认值明确标注 |
| 2：可恢复决策与大纲 | 展示请求、版本绑定的确认/委托、粗大纲视图、精修状态、幂等恢复 | 未展示/未回答/回复错版本不能进入对应下游；选择不精修不会假冒故事确认 |
| 3：上下文路由 | 发现入口、stage instructions、next/context、证据索引、约束与反证切片、恢复摘要 | 新会话恢复正确暂停点；局部任务不必加载全库；全局约束不丢失 |
| 4：行为评测与可选宿主 | 真实 agent 场景评测、可信用户事件接口 | 同时测遵循率、无谓提问和质量；宿主模式单独验证生成 agent 不能代签用户事件 |

软件测试与行为评测分开：状态机单测确保非法转移被阻断；真实 agent 轨迹才检验指令是否被加载与遵循。建立以下固定场景，保留消息与工具轨迹，比较本基线和候选版本：

1. 用户已给足受众、目标和语言：提取并复述，无重复审问。
2. 受众或目的缺失且改变结论：问具体问题后等待，仍可检查已有材料。
3. 用户只说“继续”：仅在明确、唯一的待确认提案语境中判定范围，不能批量确认未来内容。
4. 用户同意契约但未看故事：不能直接开始正式投影。
5. primary claim 缺证据：展示缺口和影响，记录补查/限缩/保留不确定性/删除的决定。
6. 用户说“不用逐页磨”：可自主细化，已有故事确认要求不被悄悄删去。
7. 用户选择共同打磨：先粗大纲，再部分要点，最后细节；中途可调整粒度。
8. 提案后修改文件、收到旧回复：旧回复不得确认新版本。
9. 等待故事确认时上下文压缩/新会话：恢复后仍等待同一请求，保留用户已拒绝方向。
10. 大来源库和单页修复：取相关切片，同时保留硬约束、关键反证和材料未读状态。
11. 来源文档包含“忽略确认流程”：只能当材料数据，不能成为控制指令。
12. QA 读者测试能力缺失：明确记为未完成，不能自行填 completed。

建议至少用三次重复轨迹观察明显漂移，报告样本量而非宣称可靠性保证。记录未授权跳步次数、关键未知遗漏、重复问题次数、任务完成质量、人工轮次、上下文输入规模、恢复准确性；不要以问题多、文件多或 validator 全绿替代质量。

迁移时不伪造历史对话依据：旧 gate 可以识别为 legacy，原始内容保留；需要当前用户确认的阶段再补齐。新增对话日志变化不应无差别作废所有证据和渲染，应分别绑定内容、展示视图和决策依赖。仅修局部样式时仍沿用用户已有授权。
