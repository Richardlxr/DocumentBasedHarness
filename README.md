# DocumentBasedHarness

> **把一堆材料，变成一场能说服人的汇报。**
> 材料进来，事实打底，契约、故事和大纲逐层对齐，幻灯片 / 网页 / 报告一起出来——
> 每个数字有出处，样式、动画、素材、语气都靠说，每次修改只动该动的那层。

---

## 这是个什么东西？

周五下午，你手里有：一份 CSV、几段实验日志、一张结果截图、半篇没写完的说明。
下周三，你要用这些说服客户：这个方案值得上。

一般的做法是打开 PPT 开始搬字。搬着搬着就会发现：数字对不上、逻辑断在第三页、
报告和幻灯片各说各话、写出来的话一股 AI 腔。

这里的做法不一样——一个**汇报编译器**。它先把材料读成一份**带出处的事实库**，
跟你对齐"讲给谁、要什么效果、说什么腔调"，设计一条**故事线**，再与你对齐各媒介的粗大纲。是否逐页精修由你选择，
确认的内容按所选媒介编译成成品：

| 成品 | 长什么样 |
|---|---|
| `deck.pptx` | 幻灯片：正文页围绕一个主要问题或结论；数据卡片、原生图表绑定事实库中的数值，其他文案和图中数字也需有证据支持 |
| `deck.html` | 网页版：单文件、离线双击可开，带出场动画（先结论、再证据、最后 so-what）、数字跳动和演讲者备注 |
| `report.md` + `report.docx` | 详版报告：书面语完整展开，Markdown 是正主，Word 是一键编译的排版成品 |

两个硬承诺：

- **数字不会飞。** 结构化数值与引用链可检查；论断数字须出自所引证据，来源真实性与语义仍需审稿；从图上
  读出来的数字会被老实标注为"估读"，只靠估读撑起来的结论会被点名。
- **改哪层，修哪层。** 系统记录每层产物的上游，依据改变后标出需要重新处理的产物，
  agent 再检查实际影响并修复；旧内容和回复留档。文件级依赖可能扩大重编译范围，不承诺自动精确到单页。

---

## 工作流：每个阶段，你可以怎样参与

你可以直接给自然语言要求，不必填写 YAML 或记住命令。agent 应把要求记入对应产物，
给你看当前方案、依据和待定项。**提出要求、接受当前版本、委托某项工作是三种不同的回复。**
一句“继续”只对应当前明确展示的提案，不代表接受尚未展示的故事、大纲和成品。

```mermaid
flowchart LR
  A[材料与目标] --> B[证据与缺口]
  B --> C[沟通契约确认]
  C --> D[故事线确认]
  D --> E[各媒介粗大纲]
  E -->|需审阅 PPTX 样式| F[模板选择与样张]
  E -->|无待定样式审阅| G[内容细化]
  F --> G
  G --> H[编译与 QA]
  H --> I[当前版本验收与交付]
```

| 阶段 | 你会看到什么 | 最适合在这里提出的要求 |
|---|---|---|
| [1. 材料与目标](#workflow-intake) | 目标复述、材料范围、优先级 | 重点看哪里，暂时不做什么，哪些材料仅作背景 |
| [2. 证据与缺口](#workflow-evidence) | 有出处的事实、计算、冲突、未读范围 | 核对数字、查看原文、保留反证、补材料 |
| [3. 沟通契约](#workflow-brief) | 受众、目标、媒介、密度、语气、约束与默认建议 | 给谁看，要多充实，用什么模板，哪些必须满足 |
| [4. 故事线](#workflow-narrative) | 不含页码和布局的逻辑链、论断及证据状态 | 先讲什么、结论是否过强、如何解释边界 |
| [5. 粗大纲](#workflow-outline) | 每页/节的职责、标题、顺序和取舍 | 拆合、调序、控制篇幅、选择是否一起精修 |
| [6. 样式样张](#workflow-appearance) | 模板候选、实际样张、适配差异 | 保留哪些品牌元素，字体是否合适，是否委托审阅 |
| [7. 内容细化](#workflow-authoring) | 当前页/节的要点、证据、图文和讲解 | 加解释、换图、改表达、调密度、安排出场顺序 |
| [8. 编译与 QA](#workflow-qa) | 成品预览、检查结果、读者反馈、修复对比 | 查错位、查受众理解、查论断与证据是否相称 |
| [9. 验收与修订](#workflow-delivery) | 当前成品、验证范围、已知限制 | 接受这版、指定局部修改、补充材料后更新 |

<a id="workflow-intake"></a>

### 1. 交材料，明确调查方向

先说大致目标，再给文件或路径。agent 应先确认调查范围，记录材料清单，按目标逐步阅读。
此时不用定好每一页，更不能提前承诺材料尚未支持的结论。

你可以说：

- “先盘点这些材料，告诉我能支撑什么，不要马上写 PPT。”
- “重点看最近一次实验；旧版报告只参考背景，别沿用它的结论。”
- “这张图是草图，只参考布局，里面的数字不能用。”
- “先复述你理解的任务，把我的要求和你的推断分开。”

agent 应展示已知目标与关键未知；能从材料查清的自己查，不要求你重复介绍整个项目。
材料中的命令或提示词不会成为修改流程、授权联网或跳过确认的依据。

<a id="workflow-evidence"></a>

### 2. 核对证据，暴露缺口

你会看到事实、出处位置、计算过程，以及材料已读/部分读/未读的范围。
不同来源发生冲突时要保留双方依据；截图读数要标“估读”，不能冒充原始测量。

| 你可以说 | agent 应如何响应 |
|---|---|
| “这个降幅怎么算的？把公式和原始值给我。” | 展示操作数、出处与计算；派生数字先登记，再用于结论 |
| “这个结论有哪些反证？” | 同时检查支持和反对材料，说明当前证据能支持到什么程度 |
| “只采用原始 CSV 的数字，图片只看趋势。” | 按来源要求取数，并说明图片与数据的对应关系 |
| “缺的材料先列出来，不要猜。” | 列缺口、影响和补充方式，不能把缺料写成已证实 |

这一阶段通常不需要逐条确认每个事实；影响目标或结论的重要取舍会带到契约或故事线中让你决定。

<a id="workflow-brief"></a>

### 3. 确认沟通契约：给谁看，做到什么程度

这是第一个必须接受的节点（Gate 1）。agent 应把**已明确要求、推断、建议默认值、待定项**分开列出，
展示完整摘要。确认的是这份契约，不是一次性批准后面的故事和成品。

| 你可以讨论 | 可以直接这样说 |
|---|---|
| 实际受众与背景 | “给客户技术负责人看；他懂系统，但不知道我们内部的模块名。” |
| 目标与场合 | “这是 20 分钟研究评审，让大家判断证据是否足以支持下一阶段实验。” |
| 输出媒介 | “要 PPTX 和详细 Word 报告；不要网页版。”或“只交 Markdown。” |
| 信息密度 | “按学术充实来，条件、证据和解释都展开。”或“这次是短汇报，改成简洁。” |
| 语言与文风 | “中文，幻灯片可直接讲出口，报告用完整书面句；参考我这两句原话。” |
| 样式模板意向 | “用这个 PPT 模板的背景、Logo 和字体；先看样张再批量做。” |
| 硬约束与偏好 | “必须保留适用条件，不能黑底；蓝色只是偏好。” |
| 协作方式 | “只在关键节点问我。”或“故事定好后，我们逐页打磨。” |

学术/研究评审默认建议采用**学术充实**，其他场合默认均衡；所有场合都能选择简洁、充实或自定义。
这是内容展开程度，与正式/口语的文风、背景/字体的样式分开。已有明确要求直接采用，
没有偏好时可以随契约接受默认值，不强迫每个人逐项选档。

你也可以要求“拿一条真实内容写两种语气让我选”“不要用‘赋能’等词”。显式禁词可机器检查；
“让非本领域读者看懂”等无法直接自动判定的硬要求，会约定人工验收办法。
模板尚未选定可约好在粗大纲后选择；与目标有关的关键未知不能悄悄略过。

<a id="workflow-narrative"></a>

### 4. 确认故事线：先把逻辑说清楚

这是第二个必须接受的节点（Gate 2）。你会看到“为什么值得关注 → 如何验证 → 得到什么结果
→ 有哪些限制 → 下一步做什么”的逻辑链，以及论断的有据、部分有据、假设、缺料状态。
顺序可以改变；此时还不分几页、摆几栏。

你可以说：

- “先给结果，再解释为什么可信；给我看两种顺序的利弊。”
- “这里最多说明相关性，不要写成已经确认因果。”
- “这条暂时作为假设，明确写出成立条件；补不了证据就删掉。”
- “结尾直接回答我们是否值得继续做，不要写‘委托方关心的价值’。”
- “先别做大纲，这条逻辑我还没认可。”

agent 应修改论断、顺序或取舍，说明依据和仍未解决的问题，再展示当前故事线。
**“不用逐页磨”“你来排版”都不能代替故事线确认。**

<a id="workflow-outline"></a>

### 5. 先对齐粗大纲，再决定怎么精修

故事线接受后，分别展示演示稿每页、报告每节的职责、标题、顺序、覆盖与省略理由。
同一个故事可以有不同的投影：现场讲述与会后阅读不必使用相同顺序或相同篇幅。

你可以说：

- “先只列每页讲什么和标题，不要一次把所有正文写满。”
- “方法细节放报告，PPT 保留能判断结果的必要条件。”
- “这页拆成方法和结果两页；不要把限制藏进附录。”
- “报告先讲方法，PPT 先讲研究问题。”
- “这个大纲可以，后续细化你来。”或“先从第一页开始一点点磨。”

粗大纲需要你接受或明确委托。默认关键节点对齐；共同打磨时按
**页/节职责 → 要点与证据 → 图文和措辞细节**逐步展开。更多选择见下方[协作档位](#workflow-collaboration)。

<a id="workflow-appearance"></a>

### 6. 定样式，看实际样张

PPTX 的样式意向在契约阶段记录，实际选择与首次适配样张放在故事线和粗大纲之后、批量细化之前。
你给了单个模板就直接按指定模板处理；给的是模板合集，agent 应先给少量候选，不把测试授权当作选定。

| 你可以说 | agent 应如何响应 |
|---|---|
| “只借背景、Logo、图标和字体，内容结构按我们的故事来。” | 分开处理样式与内容，不自动导入示例文案或内容框 |
| “先看封面、一张密集正文页和一张图表页。” | 在预览中展示代表页，说明字体替换、保留元素与适配差异 |
| “这套背景可以，但正文太小。” | 检查字号、容量与实际预览，提出内容分配或样式调整 |
| “样式你来选，也不用等我逐张审样；照约定做 QA。” | 记录明确的样式选择/审阅委托，保留后续检查与最终验收 |
| “之前样式先别用了，我要重新看。” | 重新打开样式决定，未解决前不能靠旧构建进入正式审稿与交付 |

采用已约定的默认样式可以随契约确认；首次原生模板适配通常需要样张，除非你明确委托审阅。
**委托内容精修不等于委托样式审阅。**样式接受后，同一任务内普通正文修改可复用这份决定。

样式模板提供背景、品牌元素和文字样式；内容预设提供密度与简单布局建议。
任意版式的完整风格模板编译尚未实现。原生 PPTX 模板的精确预览来自 PPTX；当前不能原样带到 HTML。
如果同时需要两种成品，agent 应先说明这个限制并对齐输出方案。

<a id="workflow-authoring"></a>

### 7. 逐页、逐节细化内容

这里开始讨论具体的图、表、解释、措辞和出场顺序。共同打磨时，每次只聚焦当前页/节；
你可以先看要点，不必一次评价整套成品。延期到这一阶段的关键问题，应先处理再定稿。

| 你可以说 | agent 应如何响应 |
|---|---|
| “这一页太空，把实验条件和结果解释补全。” | 补必要信息；证据不足时说明缺口，不靠重复标题凑密度 |
| “主图旁边放解释，结论和适用条件放在一起。” | 在现有版式能力内安排邻接关系；超出能力先说明 |
| “这三个研究问题并列展示，每块都说清要检验什么。” | 用分组和层级组织内容，避免抽象策划标签 |
| “这个术语同行也未必懂，首次出现解释一下。” | 按实际受众改写；保留影响判断的技术条件 |
| “大数字用证据里的值，不要手抄；底下说清统计范围。” | 绑定证据数值，补标签、单位和必要说明 |
| “报告展开推导，PPT 保留结论；讲稿里补背景。” | 分配到正文、备注和报告，不能把关键限制只藏在备注里 |
| “这几点按点击依次出现，最后强调结果。” | 记录动作意图，说明 PPTX 与 HTML 的实际支持差异 |
| “可以联网找两张有明确许可的历史照片。” | 在已授权范围检索、落盘并登记来源，展示选用结果 |

未授权获取外部素材时，agent 先说明用途、清单和来源再问；已经明确授权的范围不重复询问。
局部样例通过后再继续细化。共同打磨模式要求当前各页/节有接受或明确委托，才能正式编译或保存报告正文。

<a id="workflow-qa"></a>

### 8. 编译与 QA：同时检查文件和读者理解

成品由代码从已保存的计划/正文编译，渲染时没有模型重新创作内容。
机器检查引用、数字、硬约束、已知文案问题、图语法、对比度、几何等；error 会阻断相应操作。
字数提示、部分布局风险和兼容性提示仍需审阅，编译成功不代表所有页面都可读。

你可以说：

- “检查所有页的页脚和 Logo，不要只看新增正文。”
- “这处换行是不是编译引入的？在同一软件里对比原模板和成品。”
- “按甲方技术负责人的视角审一遍，删掉内部策划话术。”
- “哪些地方把‘可复现’说成了‘已经证明真实有效’？”
- “让一个不了解项目的读者只看成品，复述结论和看不懂的地方。”
- “这一页修完给我前后对比，并说明有没有影响其他页。”

agent 应检查实际渲染结果，完成逻辑、受众、语言风格和读者测试，并保留实际反馈。
读者测试只提供受众实际能接触的材料；现场讲解场景才加入实际会讲的备注。
没有独立读者或执行能力时，应报告该项未完成，不能自己填一份“已通过”。
PPTX 的验证需说明软件与字体环境，本机通过不能保证所有播放器一致。

<a id="workflow-delivery"></a>

### 9. 接受当前版本，或提出修订

完成检查后，agent 展示当前成品、验证范围、仍需注意的限制和变更说明，等你验收。
你可以说“这版可以交付”，也可以指出修改位置和原因。最终接受只绑定当前版本；
文件、依据或构建发生变化后，需重查影响并重新验收，不能沿用旧的“可以”。

你可以说：

- “P03 的图保留，把底部那句改成实际结果。”
- “这个报告我接受；PPT 的结尾还要改，先别算整套完成。”
- “给我最终文件、证据出处和已知限制。”
- “补了新实验，先告诉我哪些结论和页面会受影响。”

所选媒介分别检查，整套交付要求它们都已就绪。`comh deliver` 记录当前成品验收，
不会自动发邮件、上传平台或发布网站；这些操作需要另外明确提出。

<a id="workflow-collaboration"></a>

### 想少问一点，还是一起精修？

| 协作方式 | 你可以怎样说 | 实际范围 |
|---|---|---|
| 关键节点对齐（默认） | “契约、故事、大纲给我看，细节先由你完成。” | 这些节点分别对齐；不强制逐页确认，样式按约定处理 |
| 共同打磨 | “每次一页，从要点开始；没对齐别一次写完。” | 先大纲，后逐页/节细化，各节点接受或明确委托 |
| 委托细化 | “当前大纲后续你来完善，不用逐页等我。” | 记录委托范围；契约、故事和最终验收仍需要接受 |
| 只磨重点 | “这版大纲的 P03 一起磨，其余页委托你。” | 在共同打磨中逐项记录当前明确的接受/委托范围 |
| 单独委托样式 | “模板选择和样张审阅也交给你。” | 只改变样式决定的参与方式，不代替内容或最终验收 |

随时可以要求切换。已经明确回答的不重复问；关键未知才提问，低影响偏好给默认建议，
下游才需要的选择标明截止阶段。你可以直接问：**“现在等我决定的是什么？为什么必须现在问？”**
agent 应列当前待定项、影响和可行建议，而不是给你一整张重复问卷。

### 中途改要求，会影响哪里？

| 你改什么 | 通常需要重新处理什么 |
|---|---|
| 当前页的要点、图注或备注 | 保存该页计划；共同打磨时重审该页细节；重编译、QA 和验收 |
| 页标题、顺序、拆合或职责 | 当前媒介粗大纲及受影响细节重新对齐 |
| 背景、字体、品牌元素 | 样式适配与必要样张审阅；通常保留故事线和粗大纲决定 |
| 意外换行、重叠等机械缺陷 | 按已定效果直接修复并复检；重要品牌或字体改变仍需说明 |
| 受众、目标、媒介、全局密度或硬约束 | 更新沟通契约，重新确认契约与相关下游内容 |
| 数据、来源或核心结论 | 从证据/故事层检查影响，再更新相关计划与成品 |

“局部修改”指内容修复的范围，**不保证只重编一页或只使一项记录失效**。
当前依赖检查对部分目录和上游产物采用整体指纹，可能要求更大范围的重编译与复核；
agent 应解释影响，保留有效决定，不自动重写无关内容。
恢复任务时也可以说“告诉我当前阶段、上次否定的方案、未解决问题和下一步”，
agent 从 `next/context` 和已保存记录恢复，不用你重述整段历史。

## 样式：从选到造

**全部靠说**。你现在看到的配置和命令是 agent 的落笔处；你看到的永远是成品。

| 你说 | 会发生什么 |
|---|---|
| "换个深色的" / "要酷一点" / "像杂志" | agent 提 2-3 个方向（各一句话气质），你挑一个，浏览器里看效果 |
| "给我定制一套主题"（描述气质："赛博霓虹""水墨留白"） | 内置没命中时，agent **现场创作**整套配色/字号/字体，自动过可读性体检（正文对比度不达标不出厂），渲染样张你挑 |
| "强调色改成品牌蓝，标题再大点" | 修改样式、重渲染并核对可读性；重要变化重新展示 |
| "用我们的 PPTX 样式模板" | 一次检查背景、Logo/icon、字体，登记样式配置后编译可编辑 PPTX；用实际 PPTX 预览验收 |
| "这页放一张他年轻时的照片？" | agent 提素材方案，你点头后才检索、落盘、登记出处，出版本你挑 |
| "先把典型页做出来看看" | 粗大纲接受后制作预览；原生模板用 `render deck --preview`，普通主题也可用 `deck-html --preview`；预览不能直接交付 |

这里区分两层：**样式模板**提供背景、品牌装饰、颜色和文字样式；**风格模板**提供
排版密度、页面结构和内容组织。原生 PPTX 模板导入只处理样式；原模板的双栏框、内容槽位和
节奏不导入，现有排版引擎继续组织内容。密度与简单布局建议由下面的内容预设单独管理；
完整的风格模板编译仍未实现。

指定 PPTX 走 `style-inspect → style-import → 样式配置 → 样张确认 → render deck`。
给定单模板不重复询问选择；给合集则展示少量候选。默认主题可随契约一起确认。
同一 run 中样式不变的后续内容修改复用确认，重要样式变化重新展示；异常换行直接修复并重做 QA。
原生文字也检查字体替代、可用宽度和自动适配风险；通过编译不代表跨播放器不会错位。
完整命令、契约、失败规则及限制见[样式编译指南](comh/instructions/references/pptx-style.md)。
`theme-from-pptx` 仍是较轻量的色板/字体提取，不能替代原生背景与品牌元素导入。

**学术场合默认采用“学术充实”内容预设**：围绕一个主要问题，充分展开条件、证据、解释与
结论。布局可参考“并列问题”“主图配相邻解释”“分步方法”“逐项回答加后续验证”。
用户可随时改为均衡、简洁或自定义范围；非学术场合也能选择学术充实。
在首次沟通契约中一起明确场合与密度，不另开强制选择轮次。预设不改变背景和字体，
不靠缩字、重复文案或补造证据凑充实度。
配置与 `comh presentation-profiles` 用法见[内容预设](comh/instructions/references/presentation-profiles.md)。

**文案要能直接对实际读者说**。“委托方最终关心的价值”等内部策划话术，以及明确空标签，
会在保存/渲染前被阻断；堆叠术语、抽象背书和较长重复文字会提示审阅。
真正的研究条件和限制必须保留并解释清楚。这些检查覆盖已知可见文字字段，仍需 agent
结合受众做语义审稿，不能用 lint 通过代替内容质量判断。详见[受众文案规则](comh/instructions/references/audience-copy.md)。

五个内置方向兜底，从严谨到吸睛：

| 方向 | 气质 | 适合 |
|---|---|---|
| tier1-light | 干净留白、蓝笔标注 | 学术汇报、评审 |
| slate-tech | 浅石板底、靛蓝 | 客户技术评审 |
| midnight | 深色舞台 | 大屏发布、路演 |
| poster-pop | 海报波普：奶油纸+朱红+超大字 | 创意提案、发布周 |
| gallery-noir | 画廊黑金：暖黑+象牙+鎏金衬线 | 颁奖、作品集 |

创意和艺术向是一等公民，不是附带功能。气质没被命中就现场生成一套——
AI 负责创作，机器负责体检，生成是正门不是变通。

**背景图**也可单独指定。系统对支持的背景图做对比度估计并调整蒙层，实际可读性仍需预览核对；
HTML 将本地图片处理后内联，适合离线查看。大图较多时还应检查文件体积。

效果超出当前版式引擎（比如任意网格或完全自由的手工排版）时，agent 应说明缺少的能力，
给出可实现的选项。几何检查、文本测量和实际预览共同减少溢出与遮挡，不提供跨播放器的零错位保证。

## 动画：说什么，出什么

动画在这套系统里是**沟通决策**，不是装饰：先亮结论还是先铺证据、哪句话值得
单独一次点击，直接决定观众记住什么。所以动画也是在对话里定的：

| 你说 | 会发生什么 |
|---|---|
| "这三个要点一个一个出" | 编排点击出场；PPTX 需开启实验性动画，并核对实际构件粒度与播放效果 |
| "先亮结论，再一条条给证据" | 用共同的动作计划指定顺序，各输出按支持范围执行 |
| "最后强调这一条" | HTML 支持强调/高亮；当前 PPTX 仅支持出场/淡入，需说明降级或调整方案 |
| "翻页用 fade" | 翻页过渡切换：fade / push / wipe / cut |

网页版还自带两层**微动效**，不用你说、自动就有：

- KPI 大数字进场时从 0 跳到位（约 0.8 秒），柱状图从 0 长出来；
- 观众系统开了"减少动态"（prefers-reduced-motion）时，这两类微动效关闭，显示终值。

动作计划保持小词表，但两个输出的能力并不完全一致。PPTX 动画需显式开启，当前支持
出场/淡入；强调、延时等意图不能视为两端等价实现，应查看渲染报告并在目标播放器验证。
用户可以要求静态版、简化动作或只在 HTML 中演示效果；视差滚动、自动播放的剧场式演出不在当前支持范围。

## 不调样式的话，默认拿到的是白板吗？

不是。默认就是一套**成体系的设计储备**，开箱即用：

- **五套内置主题**（palette + 字号 + 中英字体，学术到创意艺术全覆盖）；
- **五种版式原型**：标准图文页 / 图文分栏（hero_split）/ 全幅背景+悬浮卡
  （fullscreen_backdrop）/ 时间轴（timeline，3-4 节点）/ 双栏对比（versus）；
- **排版构件**：标题、眉标（kicker）、页码页脚、分隔线和页顶强调条；
- **内容构件**：大数字 KPI 卡（渲染时从证据取数）、原生图表、mermaid 示意图
  （确定性布局）、底部结论条、展开式要点卡；
- **5,130 个语义图标**（MIT），按名字引用，颜色自动跟主题；
- **输出检查**：引用、数字、约束、文案、主题及布局等检查，结合实际成品审阅。

不自定义样式也有默认主题和版式可用；agent 仍需按你的内容量选择适合的组织方式并完成 QA。

## 凭什么信它

- **阶段决策检查。** 契约、故事线、大纲须有当前版本的接受或适用的委托记录。
  错版本回复、漏答关键问题、遗漏共同打磨的页/节会阻断后续命令。
- **验收有清单。** 自动化回归与成品体检检查：悬空引用、无据结论、
  数字漂移、静默丢内容、图语法错误、图标名写错、元素遮挡、越界、AI 腔、
  密度超载、主题对比度、素材出处……
- **AI 做判断，代码管合同。** 该灵活的地方（叙事模式、语言风格、视觉主题、
  内容取舍）由 agent 结合上下文处理；阶段决定、引用关系、可检查的硬约束和受支持的渲染契约
  由代码校验。不能自动证明的语义与受众理解保留为审稿职责。

最近一次[全流程审查](docs/reviews/2026-09-03-full-workflow-audit.md)包含组合交付与局部修订回归，
也列出了机器检查和人工判断的边界。

## 设计原则（八句话）

内容逻辑先于视觉设计 · 报告和幻灯片是同一故事的两个投影 ·
词库只供词汇不划边界（风格、主题、叙事、动画皆是）· 用户硬约束 > 偏好 >
已确认 spec > 推断 > 默认 · 保存显式产物而非隐藏思维链 ·
证据→论断→故事→投影→成品步步可回溯 · 修复在归属层进行 ·
观众是最终消费者——优化他们记住了什么，不是你想倒什么

### 工作流校验边界

- `save/confirm/render` 只检查本阶段及上游，不读坏掉的旁支草稿。
- `validate all` 按 brief.media 检查；只选幻灯片时不要求报告，Markdown 可以独立交付。
- 最终交付要求当前输入对应的成功构建、有效的内容/样式决定、当前模型审稿、所有硬约束通过及用户验收。
- 未提供派生公式时会提示未复算；数字集合检查不能证明来源真实性或论断逻辑。
- CLI 记录是 `agent_attested`：核验顺序、版本和依据字段，不能认证真人或证明模型真正理解。
- 上下文包按阶段加载；不能控制宿主已加载的消息或实际压缩策略。
- 旧确认无请求依据时保留为 legacy，不补造历史回复；需补当前确认。旧构建和审稿按迁移说明更新。
- 读者测试需实际输出文件及执行信息；代码能核对存在和版本，不能单独证明审阅独立性。

审稿格式与 `comh review` 用法见
[QA 阶段说明](comh/instructions/stages/qa.md)。
