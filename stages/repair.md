# Stage: Repair（修复循环）

用户对成品不满意时的诊断与修复协议。核心认识：**症状在成品上，病根在任何一层。**
诊断 = 沿链条下钻，找到"第一个背叛了上一层意图的地方"。

```
成品症状 → 结构化投诉 → 组证据包 → 六问诊断 → 修复提案 → 用户放行 → 修 → 复检 → 前后对比
```

## 1. 结构化投诉

把用户的模糊反馈整理成：`{成品, 位置(页/节), 方面, 原话}`。一条不满可能拆成多条
投诉，分别处理。

## 2. 组证据包（机械操作）

不要重读所有材料。用：

```
comh evidence-pack deck P07      # 或 report R02 / narrative S04
```

抽出该节点的完整切片：页面/章节 + beat + claims + evidence + sources。

## 3. 六问诊断（从便宜到贵：代码能查的先查，模型判断跟上，用户重拍板最后）

| # | 问题 | 手段 | 病根层 |
|---|---|---|---|
| 1 | 渲染忠实于 plan 吗？ | 读回成品逐字段比对 plan；截图查溢出/重叠/对比度 | `deck_plan`(renderer bug) / renderer |
| 2 | 忠实渲染了但还是丑？ | 看截图判断 | 风格层（换模板，内容不动） |
| 3 | plan 忠实投影了 beat 吗？ | 比对 page.title/points vs beat.message/claims | `deck_plan` / `report_plan` |
| 4 | beat/claim 本身成立吗？ | 叙事自检（逻辑链、跳跃、结论可推性） | `narrative` |
| 5 | 数字和事实有据吗？ | `comh validate all` + 证据包核对 | `evidence` |
| 6 | 方向本身对吗？ | narrative 忠实服务 brief 但用户不认 | `brief`（重过 Gate 1） |

兜底：链条断在最上游（材料根本没有）→ 材料层，与用户商量补料/补调研。
每层都问同一句话："我是否忠实执行了上一层？"第一个答"否"的地方就是病根。

## 4. 修复提案（先亮影响面再动手）

- **明确授权范围内的局部修改直接执行**：先说明归属层与影响，再修改、复检、展示差异。
- **改变目标、核心结论或超出授权范围时先提案**：说明病因、改法、下游影响，用户放行后执行。
  brief/narrative 内容发生变化仍需重新过对应 Gate。
- **渲染层修复（renderer/模板/编译）：直接执行**，无破坏性。

## 5. 修复与复检

在归属层改 artifact → `comh save <artifact>`（下游自动标脏）→ 重跑受影响 stage →
`comh validate all` → 重新渲染 → 更新当前版本 `comh review` → 给用户看**前后对比**（改了哪页/哪节、diff 是什么）。

## 6. 保险丝与台账

- 每次修复追加记录到 `qa/repair-journal.yaml`：
  `{date, complaint, diagnosis, owning_artifact, action, outcome}`。
- **同一投诉修复两次仍不满意的，禁止第三次同向硬修**：换诊断假设（通常是更深层），
  并把整条 ID 链摊开给用户看，让用户指认病根。两次修不好，说明诊断可能错了，
  升级比硬修便宜。
